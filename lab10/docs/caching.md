# Что кешируем, ключи, TTL, инвалидация

Кеш устроен по схеме cache-aside, всё через `App\Core\Cache::remember()`:
1. проверить Redis;
2. при попадании (HIT) вернуть копию;
3. при промахе (MISS) взять данные из базы;
4. положить их в Redis с временем жизни и вернуть.

Класс `Cache` перенесён из примера без изменений. В настройках (`config/app.php → cache`) изменён только префикс ключей: `vetclinic:`.

Кеширующие модели наследуют обычные и переопределяют только нужные методы:
- `CachedAppointmentRepository`
- `CachedDoctorRepository`
- `CachedAnimalRepository`
- `CachedOwnerRepository` (без кеша чтения, только инвалидация)

Контроллеры подключают их одной строкой в конструкторе. Ключи и правила инвалидации собраны в одном месте — `app/Models/ClinicCache.php`, чтобы при записи и при удалении ключ назывался одинаково.

## Выбор данных

| Данные | Адрес API | Как часто читают | Как часто меняют | Сколько стоит получить | Решение |
|---|---|---|---|---|---|
| справочник врачей | GET /api/doctors | при каждом открытии и обновлении страницы (форма записи) | редко, только администратор | мало: 50 строк | кешируем: запросов очень много |
| справочник животных | GET /api/animals | при каждом открытии и обновлении страницы | при регистрации нового животного | заметно: 5 000 строк и подзапрос имени владельца на каждую | кешируем |
| карточка приёма | GET /api/appointments/{id} | при открытии приёма | при каждом изменении приёма | очень мало: одна строка по первичному ключу | кешируем по заданию; измерения показали, что выигрыша почти нет |
| список приёмов с фильтрами | GET /api/appointments?... | при каждом обновлении списка, поиске, смене фильтра | при каждой записи на приём | дорого: страница строк и COUNT по 500 000 строк, поиск по подстроке — полный просмотр таблицы | кешируем, ключ из всех параметров |
| отчёт по врачам | GET /api/reports/doctors | часто: администратор и врачи смотрят загрузку | при каждой записи и изменении приёма | очень дорого: группировка по всем приёмам и услугам | кешируем |
| владельцы | GET /api/owners | только в форме «Новое животное» | при регистрации | мало | не кешируем |
| история приёмов животного | GET /api/animals/{id}/appointments | редко, по одному животному | — | мало: индекс по `animal_id` (ЛР №8) | не кешируем |
| проверка занятости врача | при записи на приём | — | — | — | никогда не кешируем: устаревшая копия позволила бы записать двух животных на одно время |

## Ключи и время жизни

| Данные | Ключ (в Redis с префиксом `vetclinic:`) | TTL | Почему так |
|---|---|---|---|
| справочник врачей | `doctors:all` | 300 с | меняется редко; 5 минут — страховка, если инвалидация где-то не сработает |
| справочник животных | `animals:all` | 300 с | то же |
| карточка приёма | `appointments:item:r<R>:<id>` | 60 с | номер приёма в ключе: у каждого приёма своя запись |
| список приёмов | `appointments:list:v<V>:r<R>:<md5>` | 60 с | в md5 входят все параметры: статус, животное, врач, поиск, сортировка, limit, offset |
| отчёт по врачам | `report:doctors` | 120 с | один ключ: отчёт не зависит от параметров |
| версия списков приёмов | `appointments:version` (V) | без TTL | счётчик для массовой инвалидации списков |
| версия справочников | `refs:version` (R) | без TTL | счётчик: имена врачей, животных и владельцев есть в карточках и списках приёмов |

Пример ключа списка: `vetclinic:appointments:list:v0:r0:8ea2d76e6cbaf5836624e4a60f4fd266`. Он строится так:

```php
'appointments:list:v' . Cache::version('appointments:version') . ':r' . Cache::version('refs:version')
    . ':' . md5(json_encode([$status, $animalId, $doctorId, $q, $sort, $limit, $offset]));
```

**Зачем вторая версия (`refs:version`).** В карточке и в списке приёмов сервер отдаёт имена врача, животного и владельца (ЛР №9, расхождение №6). Если переименовать врача, устареют все карточки и списки, где он есть, а найти и удалить их по одному нельзя. Поэтому номер версии справочников входит в ключи карточек и списков. При изменении врача, животного или владельца номер растёт, и все такие ключи разом перестают использоваться, а старые записи Redis удалит сам по истечении TTL.

## Инвалидация: что изменилось — что удалить

| Что изменилось | Что удаляется или обновляется | Где |
|---|---|---|
| создан приём | `appointments:version` +1 (все списки), `report:doctors` | `CachedAppointmentRepository::add` → `ClinicCache::appointmentsChanged()` |
| изменён или удалён приём | `appointments:version` +1, `report:doctors`, карточка `appointments:item:r<R>:<id>` | `update`, `delete` |
| создан или изменён врач | `doctors:all`, `report:doctors` (в нём имена), `refs:version` +1 (карточки и списки с именем врача) | `CachedDoctorRepository::add`, `update` → `ClinicCache::doctorsChanged()` |
| удалён врач | то же и `appointments:version` +1: в базе у его приёмов `doctor_id` становится NULL (`ON DELETE SET NULL`) | `CachedDoctorRepository::delete` |
| создано животное | `animals:all` | `CachedAnimalRepository::add`: нового животного ещё нет в приёмах |
| изменено или удалено животное | `animals:all`, `refs:version` +1 | `update`, `delete` → `ClinicCache::animalsChanged()` |
| изменён владелец | `animals:all` (в нём имена владельцев), `refs:version` +1 | `CachedOwnerRepository::update` |
| удалён владелец | `animals:all` | `CachedOwnerRepository::delete`: удалить можно только владельца без животных |
| создан владелец | ничего | у нового владельца ещё нет животных |

Каждое правило проверено автотестом раздела 7 (`tests/api-tests.php`). После изменения следующий запрос отвечает `X-Cache: MISS` и содержит новые данные. Кроме того, все 89 проверок ЛР №9 проходят с включённым кешем, то есть нигде не остаются устаревшие копии.

## Устойчивость

Кеш — ускоритель, а не обязательная часть:
- подключение к Redis идёт с таймаутом 0,5 с;
- любая ошибка Redis перехватывается (`RedisException`), после первой неудачи в этом запросе Redis больше не спрашивается;
- данные берутся из базы, а ответ получает заголовок `X-Cache: BYPASS`.

Проверено остановкой Redis: клиент работает, все ответы 200 с `BYPASS`. После запуска Redis кеш снова даёт HIT ([снимок](../images/redis-bypass.png)).

Кеш не обходит защиту: «охранник» и `require_role` срабатывают до обращения к кешу. Поэтому без токена по-прежнему 401, а регистратор не получит отчёт даже из кеша (403).
