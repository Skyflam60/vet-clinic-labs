# Устройство очереди

## Ключи Redis

Очередей две, у каждой одинаковый набор ключей (все с префиксом `vetclinic:`):

| Ключ | Тип | Что хранит |
|---|---|---|
| `queue:default`, `queue:reports` | список | ожидающие задачи |
| `queue:<имя>:processing` | список | задачи «в работе»: воркер взял, но ещё не подтвердил |
| `queue:<имя>:delayed` | упорядоченное множество | задачи для повтора; оценка — время, когда вернуть их в очередь |
| `queue:<имя>:dead` | список | «мёртвая» очередь: задачи, не выполненные за 3 попытки |
| `queue:<имя>:reserved` | хеш | номер задачи → время, когда воркер её взял (для восстановления) |

Письма идут в `default`, отчёты в `reports` (`Jobs::queueFor()`). Если бы очередь была одна, письмо о переносе приёма ждало бы, пока воркер построит отчёт по 500 тысячам приёмов.

## Путь задачи

```
обработчик запроса  Jobs::dispatch() → Queue::push()     LPUSH queue:default
воркер              Queue::reserve()                     BLMOVE queue:default → queue:default:processing, HSET reserved
                    Jobs::run()                          NotificationJob::handle() или ReportJob::handle()
    успех           Queue::ack()                         LREM processing, HDEL reserved
    ошибка          Queue::fail()                        ZADD delayed (попытки 1–2) или LPUSH dead (попытка 3), затем ack
    пауза прошла    Queue::promote()                     ZREM delayed → LPUSH queue:default
    после сбоя      Queue::recover()                     LREM processing → RPUSH queue:default
```

Новая задача кладётся слева, берётся справа, поэтому первой выполняется самая старая. Восстановленная задача кладётся справа: она ждала дольше всех и выполняется первой.

## Формат задачи

```json
{"id": "ef1b4a7c744179da", "type": "notification",
 "payload": {"appointment_id": 1, "event": "cancelled", "email": "ivanov@example.org", "owner": "Иванов И.И.",
             "animal": "Рекс", "title": "Плановый осмотр", "date": "2026-11-01T10:00", "doctor": "Иванова"},
 "attempts": 0, "created_at": "2026-11-20T21:10:41+00:00"}
```

```json
{"id": "4eefa591043daf34", "type": "report", "payload": {"report_id": 1}, "attempts": 0, "created_at": "..."}
```

Что кладём в payload:
- **Письмо:** снимок того, что нужно для текста письма в момент события. Если приём потом удалят или переименуют животное, письмо «приём отменён» всё равно уйдёт с правильным текстом. Целую запись приёма не кладём: в ней лишние поля (номера, статусы), а очередь не должна раздуваться.
- **Отчёт:** только номер заявки. Период и статус хранятся в таблице `report_requests`, туда же воркер пишет результат: статус, число строк, выручку, имя файла, текст ошибки.

## Гарантии и надёжность

| Что случилось | Что делает система |
|---|---|
| обработчик бросил исключение | повтор через 2 с, затем через 4 с; после 3 неудач — в `dead` с текстом ошибки |
| воркер убит посреди задачи (`kill -9`) | задача остаётся в `processing`. Новый воркер при запуске и каждые 10 с возвращает в очередь задачи, взятые больше `QUEUE_STUCK_AFTER` секунд назад (по умолчанию 120) |
| воркер остановлен Ctrl+C или `kill` | сигнал только снимает флаг: текущая задача доделывается, затем воркер выходит |
| Redis недоступен при постановке | `Jobs::dispatch` возвращает `null`, ошибка пишется в журнал PHP. Приём сохранён, письмо потеряно. Заказ отчёта отвечает 503, заявка помечается `failed` |
| воркер не запущен | задачи копятся в очереди и выполняются, когда воркер запустят |

**Как минимум один раз.** Задача может выполниться дважды: например, воркер записал письмо в журнал, но упал до `ack`. Поэтому обработчики идемпотентны:
- **Письмо:** в `notifications` пара `(job_id, recipient)` уникальна, запись идёт через `INSERT ... ON CONFLICT (job_id, recipient) DO NOTHING`. Повтор той же задачи второго письма не создаёт (проверено автотестом). В настоящей почте нужен тот же приём: сначала проверить журнал, затем отправлять, или передавать почтовому сервису номер задачи как ключ идемпотентности.
- **Отчёт:** повтор перезаписывает тот же файл `report-<номер>.csv` и ту же строку заявки. Дубля не бывает.

**Срок выполнения.** Воркер не может отличить «другой воркер выполняет задачу» от «другой воркер умер», поэтому смотрит, сколько времени задача в работе. Срок `QUEUE_STUCK_AFTER` должен быть больше самой долгой задачи: отчёт по 500 тысячам приёмов строится около 3,5 с, срок 120 с. Благодаря сроку запуск второго воркера не забирает задачу у первого (автотест раздела 11).

## Ограничения

- Задача ставится в Redis после записи в базу, но не в той же транзакции. Если Redis упал между этими шагами, письмо потеряется. Надёжнее схема outbox: задача пишется в таблицу базы той же транзакцией, что и приём, а отдельный процесс переносит её в Redis.
- Redis в `docker-compose.yml` без тома и без журнала AOF: если контейнер пересоздать, очередь пропадёт. Для эксплуатации нужны том и `appendonly yes`.
- Если задача выполняется дольше срока `QUEUE_STUCK_AFTER`, её возьмёт второй воркер, и она выполнится дважды.
- «Мёртвые» задачи никто не разбирает автоматически: их видно в `GET /api/queue/stats` и `php bin/queue-stats.php --dead`.
- `promote` и `recover` выполняют несколько команд Redis, а не одну атомарную. Двойной возврат исключён тем, что задачу возвращает только тот, кому удалось её удалить (`ZREM` или `LREM` вернули 1).
